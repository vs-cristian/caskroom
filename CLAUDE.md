# CLAUDE.md

## What this is

Caskroom — personal macOS GUI for Homebrew (macOS 15+, Apple Silicon; Liquid Glass on macOS 26+). Lists installed formulae/casks, shows and applies updates, searches and installs, and manages `brew services`. It shells out to the `brew` CLI and decodes its JSON; it never reimplements Homebrew logic or reads Homebrew's internal files. Other network sources: Homebrew's public API on formulae.brew.sh (install analytics for Discover and the package page, the executables database for command search, the cask list for Adopt, the formula list for the Background Services collection), package homepages / GitHub for logos, GitHub release feeds and apps' Sparkle appcasts for release notes, and OSV.dev through `brew vulns`, only once turned on.

The name is Homebrew's word for the folder casks install into (`/opt/homebrew/Caskroom`). A `Caskroom` path in brew's output or the fixtures is that folder, not this app.

The UI follows Apple's own macOS 26/27 apps (Liquid Glass): App Store for Discover, Updates and the package page; System Settings ▸ Login Items for Services; Xcode's activity view for the toolbar status pill.

## Commands

```sh
make run                     # release build, assemble build/Caskroom.app, open it
make app                     # build + assemble .app without launching
swift build                  # debug build (compiles; looks pre-glass, see below)
make debug                   # debug build that looks like the release
swift test                   # unit tests (fake brew script, JSON fixtures)
swift test --filter ParserTests
make debug && CASKROOM_SNAPSHOT_DIR=/tmp/shots .build/debug/CaskroomApp   # PNG of every page, then quits (CASKROOM_APPEARANCE=dark for dark)
make screenshots             # the site's screenshots into docs/assets, light and dark, real window captures (~30 s)
CASKROOM_BREW_TESTS=1 swift test --filter LiveBrewTests            # read-only checks against real brew
CASKROOM_BREW_MUTATE=1 swift test --filter LiveBrewMutationTests   # installs then uninstalls `tree`
Support/release.sh --dry-run 0.2.0                                  # build/Caskroom-0.2.0.zip + build/caskroom.rb, nothing published
```

`Support/release.sh <version>` (with `SIGN` and `NOTARY_PROFILE`) is the whole release: `make app` with a Developer ID identity (hardened runtime, `Support/Caskroom.entitlements`), notarise, GitHub Release on `vs-cristian/caskroom`, cask pushed to `vs-cristian/homebrew-tap`. It refuses to publish an ad-hoc build. `SIGN="Developer ID Application: CORINA BOTNARI (JH3TR8UJG6)" NOTARY_PROFILE=caskroom` are this Mac's values; with both set, `--dry-run` signs, notarises and staples without publishing.

Use `make run` to check app behaviour: it launches through LaunchServices with a bare PATH, as Finder does.

## Architecture

`CaskroomApp → BrewKit`, plus `CaskroomAskpass`.

- **BrewKit** — no UI imports, Swift language mode v5.
  - `BrewRunner` runs brew. Every command goes through `stream()`; `run()` collects its stdout. Both pipes are drained on their own threads, and exit is observed via `terminationHandler` — `waitUntilExit` on a dispatch worker hung in tests. stdin is `/dev/null`, so anything that prompts fails instead of hanging; sudo asks through `SUDO_ASKPASS` instead (see `CaskroomAskpass`). Cancel sends SIGTERM to brew's process group (`Process` makes brew its leader), so curl, installers and sudo's prompt stop too, even if brew itself already exited. stderr is ignored unless the exit status is non-zero (brew prints warnings there). `HOMEBREW_NO_AUTO_UPDATE=1` unless the caller allows auto-update.
  - `BrewParser` decodes `brew info --json=v2`, `brew outdated --json=v2` and `brew services info --all --json` (`list --json` has the same rows without pid, log paths or `registered`). Fields are optional and unknown keys ignored, so Homebrew schema changes don't break decoding. A package's `deprecation`/`disabling` (`Deprecation`: reason, replacement, date) come from the `deprecation_*`/`disable_*` fields; `disabling` is also set for a deprecated package that already has a disable date. Fixtures in `Tests/BrewKitTests/Fixtures` were captured from a real install (`outdated.json` is hand-written: nothing was outdated; in `services-info.json` the mysql entry was edited to running, since nothing was).
  - `BrewOperation` — every mutating command, its `steps` (each a brew invocation; most operations have one; a step that names a package passes `--formula`/`--cask`, except `version-install` and `services`, which take only formulae and have no such flag) and whether it may auto-update (install/adopt/upgrade/reinstall only). `command` joins the steps with `&&`. `BrewService.perform` runs steps in order, logs `==> brew …` before each when there are several, stops at the first failure and runs `rollback(afterCompletedSteps:)` (detached, so it survives a cancel). `upgradeAll(greedy:casks:)` with a cask list is `upgrade --formula` then `upgrade --cask <those>`: brew has no way to exclude a cask. `revert` is `[tap --force homebrew/core] && unlink && version-install <name> <version>`, relinking on failure: `brew extract` (inside `version-install`) needs homebrew/core tapped, which it isn't under the API, and the old version installs as `name@version`, which would clash with the linked current one. `upgradeVulnerable` is `upgrade --formula --vulnerable`. Services: `start` runs and registers at login, `stop` stops and unregisters, `run` runs without registering, `kill` stops but stays registered; brew has no register-only or unregister-only command. `adopt` is `install --adopt` over an app already in place (brew refuses unless it's the cask's version, except for `auto_updates` casks); `zap` is `uninstall --zap`; `cleanup` is plain `brew cleanup`, which also autoremoves unneeded dependencies.
  - `BrewParser.cleanup` reads `brew cleanup --dry-run`'s prose summary ("would free approximately …", "Would autoremove …"): there's no JSON for it. `BrewParser.sizes` reads `brew info --sizes` (a "name size" section per kind; it ignores `--json`, and says `0B` for a package that isn't installed), behind `BrewService.size(of:)`. `BrewService.allDependencies(of:)` is `brew deps`, recursive.
  - Package fields beyond the basics: `kegOnly`/`kegOnlyReason`/`linked` (`linked_keg`; a keg-only formula can be force-linked), `otherVersions` (`versioned_formulae`, which leaves out the unversioned one), `conflicts` (`conflicts_with`, a list for formulae, `{cask:, formula:}` for casks), `minimumMacOS` (a cask's `depends_on.macos[">="]`), `oldNames` (`oldnames`/`old_tokens`).
  - `SearchIndex` — names from `brew formulae` / `brew casks`, searched locally; details come from `brew info` when a page opens. `added(since:)`/`removed(since:)` diff two indexes for New in Homebrew.
  - `CommandIndex` — `executables.txt` (`name[(version)]:cmd cmd…`), the database `brew which-formula` reads, fetched from formulae.brew.sh rather than read from brew's cache; the app keeps it a day in `~/Library/Caches/io.github.vs-cristian.caskroom/executables.txt`. Case-insensitive prefix search, grouped per command, unversioned formulae first.
  - `ReleaseNotes` / `ReleaseSource` — an installed cask's `SUFeedURL` (its app's Info.plist) or a GitHub repo found in the download URL, `head` URL or homepage, read through `releases.atom` (no API, no rate limit, last 10 releases). `between` picks the releases after the installed version up to the current one, matching tags loosely (`v1.2`, `jq-1.2`) and, for GitHub, only tags of the current one's family (ripgrep also tags `ignore-0.4.34`). HTML becomes plain text in `text(fromHTML:)`, not through an HTML renderer, which would fetch images. A formula's `_N` rebuild suffix is dropped first (`PackageKind.upstreamVersion`).
  - `BrewService.vulnerabilities()` — `brew vulns --json`, which exits 1 whenever it finds something (or couldn't check everything), so parseable stdout wins over the exit status. Findings are matched to installed formulae by the last component of brew's tap-qualified name. `VulnerableFormula.isFixed(by:)` is nil when OSV.dev's fixes are commits rather than comparable versions.
  - `SelfUpgrade` — updates the app running brew, which brew can only replace once it has exited: a `/bin/sh` spawned in its own session (`POSIX_SPAWN_SETSID`, so quitting's SIGTERM to brew's groups misses it) waits for the app's pid, runs the brew command with output to `SelfUpgrade.log.partial`, appends an exit-status marker, renames it to `SelfUpgrade.log` and, if asked, `open`s the app again. `pickUp()` reads and deletes the log; no status means it stopped before brew exited.
  - `AdoptionIndex` — formulae.brew.sh's `cask.json` (about 20 MB, read with `JSONSerialization`) reduced to app bundle name → cask tokens.
  - `ServiceIndex` — formulae.brew.sh's `formula.json` (about 30 MB, 5 MB compressed) reduced to the formulae with a `service` block.
  - `HomebrewAnalytics` — install rankings over 30 and 90 days (`ranking`: rank and count, every package Homebrew counted; formulae by installs on request). `climbing` compares the two for Trending: within the 30-day top 300, 90-day rank over 30-day rank of at least 1.5, biggest ratio first. `monthlyInstalls(of:)` reads one package's API page, for packages the rankings don't have. Tap-qualified names are dropped: `brew info` can't resolve them without the tap.
  - `LogoLocator` — where a package's logo comes from. A GitHub homepage gives the owner's avatar, but only for organisations (a user's avatar is a face); the API call for that is rate-limited to 60/hour, hence the disk cache. Any other homepage: its `<link rel=…icon>` tags, largest first, then `/apple-touch-icon.png`, then `/favicon.ico`. Code hosts (GitLab, SourceForge…) are skipped, since their icon is the host's brand.
- **CaskroomAskpass** — the `SUDO_ASKPASS` program. Homebrew runs `sudo -A` when it sees that variable, and sudo runs this: an `NSAlert` with a password field, the password on stdout, non-zero exit on cancel. It refuses to run unless its parent is `/usr/bin/sudo`, so nothing else can read a password from it. `make app` puts it in `Contents/Helpers` and signs it before the app; `CaskroomApp` falls back to the copy beside its executable in a `swift build` tree. sudo skips Touch ID (`pam_tid`) in askpass mode, so when `SudoTouchID` finds it enabled in `/etc/pam.d/sudo_local` or `/etc/pam.d/sudo`, `BrewRunner` leaves `SUDO_ASKPASS` unset and sudo shows the Touch ID sheet itself. Cancelling that sheet fails the command: with no terminal, sudo can't fall back to a password.
- **CaskroomApp** — SwiftUI. `BrewStore` (`@Observable @MainActor`) holds all state.
  - The bundle ID is `io.github.vs-cristian.caskroom` (`Support/Info.plist`). `AppFolders` spells it out again for the caches and Application Support folders, since a `swift build` binary has no bundle, and so do the cask's `zap` paths in `Support/release.sh`: change all three together.
  - Mutations go through `enqueue` and run one at a time (Homebrew takes a global lock). Each finished operation triggers `refresh()`; refreshes that arrive mid-load coalesce into one more pass.
  - Navigation is a two-column `NavigationSplitView`: `sidebar` (a `SidebarItem`) picks the root page, and `path` (a `NavigationPath`) pushes `PackageDetailPage`s (`PackageRef`) and `DiscoverListPage`s (`DiscoverList`) over it, App Store style. Changing `sidebar` or `searchText` clears `path`. A non-empty `searchText` (the sidebar search field) replaces the root page with `SearchResultsPage`.
  - `store.package(ref)` resolves a page's package: installed, else `infoCache` (cleared on every refresh), else `catalog` (Discover's), else the Adopt scan.
  - Discover (`Discover.swift`, `DiscoverPage`): the hero is the one thing relevant now, in order: updates waiting (opens Updates), apps to adopt (opens Adopt; the page runs `scanAdoptableApps()` for the count), the top trending package, else a click focuses search. `loadDiscover()` reads the four rankings, looks up the top 200 casks with `brew info` and splits them: a cask with an app bundle (`appPath`) is an app, one without (Codex, Azure CLI, the Android SDK tools) joins formulae in Top Command-Line Tools, merged by install count. Each chart keeps 100 for its See All page; shelves show 12. Analytics names are checked against the search index first: one Homebrew removed would fail the whole `brew info`. New in Homebrew: `KnownPackages` (`~/Library/Application Support/io.github.vs-cristian.caskroom/KnownPackages.json`) keeps the last index; every index load (launch, and after each `brew update`) diffs against it and keeps additions 60 days. The first look finds nothing. `loadSearchIndex` retries a list missing a kind or under half the last one's size, with waits growing to about two minutes in all (one load at a time, `loadingSearchIndex`): brew prints little or nothing while its package data is refreshed (an update running in Terminal), and believing it once emptied Discover (every ranked name filtered out, a spinner with no error) and made the whole catalog "new". Giving up after 10 s once left search answering No Results for everything until the next update; `SearchResultsPage` now retries an empty index on each new query and says it's loading instead. `KnownPackages` also ignores any single look that changes over 1,000 names, and drops such a look already saved. Discover with empty charts is an error with Try Again, never a bare spinner. Names that disappeared are kept too, so a new name whose package lists one in `oldNames` is a rename and is left out; a tap's names (with `/`) are never new. Collections (`PackageCollection`): Fonts (casks named `font-…`) and Background Services (`ServiceIndex`) from the data, Browsers/Terminals/Editors hand-written and checked against the index, all ordered by installs this month. `DownloadCache` keeps the analytics (12 hours), `cask.json` (a day) and the services list (a week) in `~/Library/Caches/io.github.vs-cristian.caskroom`, and serves a stale copy offline.
  - List pages share `PackageRow` (32pt icon, separators aligned to the name even behind a rank). A `DiscoverListPage` opens with its description as a plain row (not a sticky header); each row's right side (`DiscoverListTrailing`) is installs this month, or for an installed service its status, with Run/Stop in place of a dead "Installed". Library rows show the version middle-truncated, "1.2 → 1.3" in the accent color for an update, and on Dependencies what uses each one (direct dependents) or Not Needed (from `store.cleanup`). Action buttons in lists share a minimum width so the column lines up.
  - `catalog` is `brew info` for packages Discover and its lists show. Unlike `infoCache` it survives refreshes, except entries whose installed state changed. Rows call `store.requestInfo(ref)` as they appear; requests within 100 ms share one `brew info` per kind (up to 100 names), and each package is asked about once.
  - `PrimaryActionButton` is the one action for a package everywhere (Install / Adopt / Update / Open / progress). Change what a package offers there, not per page. Adopt replaces Install when `store.isAdoptable(ref)`: a cask that isn't installed but whose `appPath` exists on disk.
  - Scheduled checks: `store.checkPeriodically()` (a RootView `.task`) polls every 5 minutes and, when the last successful `brew update` (`LastUpdateCheck` in UserDefaults, set by Check Now too) is over 4 hours old, queues `.update` as an `automatic` run, unless Settings turns it off. Automatic runs don't open Activity or notify on failure; instead the next load after one posts a single `Notifier.updatesAvailable` for non-pinned updates not seen before (whatever the first load found counts as seen). Clicking it opens Updates. The Dock badge is `outdated.count`, like the sidebar's, set in RootView.
  - Update history (`UpdateHistory`, `~/Library/Application Support/io.github.vs-cristian.caskroom/UpdateHistory.json`, 200 records): when an upgrade, Update All or reinstall starts, the store notes the installed versions it may change; the first load that began after it ended records each package whose version moved. Comparing versions, not the exit status, keeps an Update All that failed partway. Updates shows the last 30 days as Updated Recently (one row per package); the Activity popover lists records from before launch under Earlier. Only Caskroom's own updates are seen.
  - Self-updating casks (`auto_updates`): brew's plain `outdated` and `upgrade` include one only when the app on disk is older than the cask (Homebrew 6+ reads the bundle's version). Settings can add `--greedy-auto-updates` to both (`store.greedyAutoUpdates`, in UserDefaults, off by default): that goes by brew's install records, so an app that already updated itself stays listed until brew reinstalls it. Either way its row is tagged "Updates itself". The page's bottom banner is `store.cleanup` (a dry run at launch and after the queue drains, never blocking it).
  - Icons (`PackageIcon`, which looks the package up itself): an installed cask's real app icon; else the project logo from `LogoStore`; else the name's initial on a muted tile tinted by a stable hash of the name (a leading "lib" skipped), so logo-less packages still tell apart. `LogoStore` caches in `~/Library/Caches/io.github.vs-cristian.caskroom/Logos` (`<key>.png`, or `<key>.none` for a miss, retried after a week), runs at most 4 lookups at once, and drops logos under 32px. A miss is recorded only when a server answered: a homepage that refuses (403, 429) or fails (5xx), or icon fetches that all time out, are retried next launch. Opaque square art fills its tile; transparent marks sit on white (or on a dark tile when nearly white, as ChatGPT's), never upscaled past 1.5× their 2x size.
  - Security (`SidebarItem.security`) is off until turned on (`checksVulnerabilities`, UserDefaults `CheckVulnerabilities`), on the page or in Settings, because `brew vulns` sends formula names and versions to OSV.dev. Then it runs at launch and once the queue drains after anything that `changesFormulae`; a failed recheck keeps the last report. Fix is `.upgradeVulnerable`. Updates tags vulnerable rows, the package page shows `VulnerabilityCard`, and the sidebar badge counts findings. Casks aren't checked.
  - What's New: `ReleaseNotesStore` (environment) caches per package, installed and current version until quit. `WhatsNewView` is the package page's section and the popover behind each Updates row's What's New link. Without a feed it links the homepage.
  - Open apps: `store.runningApps` follows NSWorkspace launches and quits (`watchRunningApps`, a RootView `.task`). `isOpenDuringUpdate` is an installed cask whose app is running and whose cask has no `uninstall quit:` (`Package.quitsApp`): brew quits and reopens only those that do, and replaces the rest while they run. Such rows say Open, Update All leaves them out (`heldBack`, `canUpgradeAll`), and the primary button becomes a split Update menu whose click is Update When I Quit (`updatesOnQuit`, UserDefaults `UpdateOnQuit`). The update queues when the app quits, or at the next load if it quit while Caskroom was closed.
  - Updating Caskroom itself: `store.selfRef` is the installed cask whose `appPath` is this bundle (nil for a `swift build` or `build/` copy). It always counts as open during an update, so Update All leaves it out. `enqueue` never queues an upgrade or reinstall of it: it sets `selfUpgrade` and quits (cancelling the quit clears it), and `applicationWillTerminate` calls `handOffSelfUpgrade()`, which saves the operation and old version (UserDefaults `SelfUpgrade`) and starts `SelfUpgrade`, relaunching for Update and Relaunch but not for Update When I Quit. The next launch's `pickUpSelfUpgrade()` turns the log into a finished `OperationRun` (Activity opens if it failed) and feeds Update History.
  - Revert (`revertibleUpdate`, `requestRevert`, `RevertRequest`): a formula's latest Updated Recently record, while that version is still installed, offers Revert to the old version, after a dialog that says it makes a personal tap, will likely build from source, unlinks the current version, and, when `brew tap` doesn't list homebrew/core, fetches its history first.
  - Command search: `SearchResultsPage` has a Commands section from `store.commandIndex`, and a formula's page lists its commands (click copies). An installed formula with nothing to update shows its first three (named like the formula first, then shortest) in the header via `PrimaryActionButton(commands:)`, where the button would otherwise say a dead "Installed".
  - Package page: the info strip shows only cells that say something: one Version cell ("8.4.12 → 8.4.13" only with an update; the `_N` rebuild suffix dropped unless only it changed), installs this month, size on disk (installed only), then License and Dependencies for a formula or Requires (macOS) and Updates (itself or Homebrew) for a cask, then Source. `store.loadFacts` fills `facts`: installs from Discover's rankings, else the package's API page; size from `brew info --sizes`, per installed version; and before an install `brew deps`, for "Also installs N packages" under the button, while the Dependencies chips mark what's installed. What's New sits under the strip (3 lines a release, 2 releases). A keg-only formula that isn't linked gets `PathCard` with the `export PATH=…/opt/<name>/bin` line: brew's caveats JSON doesn't include that note. Caveats collapse to 4 lines. Other Versions (`store.otherVersions`: brew's list plus the unversioned formula; for casks, the index's `name@…`) and Conflicts With sit beside Dependencies; a conflict isn't repeated under Other Versions. Information leaves out what the strip shows; Full name only when it differs.
  - Adopt (`SidebarItem.adopt`, last in System, no badge): `scanAdoptableApps()` runs when this page or Discover first opens (its cask list is cached a day). It matches `.app`s in /Applications and ~/Applications against `AdoptionIndex`, leaving out App Store apps (`_MASReceipt`) and apps an installed cask manages, then fetches those casks with `brew info`. `store.package(ref)` falls back to them, so `PrimaryActionButton` offers Adopt as everywhere else.
  - Needs Attention (`LibraryFilter.attention`, sidebar badge `store.needingAttention`) lists installed packages that are deprecated or disabled, dependencies included, with `Package.attentionSummary` as the row subtitle. The package page's `DeprecationCard` explains why (brew's reason symbols are worded in `Deprecation.because`, after brew's own messages; a maintainer's phrase is used as written) and links the replacement.
  - Services follow Login Items: the switch is start at login (`registered`; `store.loginCommand`), and Run/Stop beside it acts only now (`store.runCommand`: `kill` keeps a registered service registered, `start` runs a registered one rather than `run`). `ServiceMenu` holds a service's commands, including Open Log; `PackageMenu` includes it so they reach the menu bar. A row in error shows Open Log inline.
  - `PackageMenu(store:ref:)` is every secondary action for a package: the context menu on every package row, the `⋯` menu on its page, and the menu bar's Package menu (`PackageCommands`, which finds the open page through the `packageRef` focused value). It takes the store explicitly because menu-bar commands have no environment. Every command must stay reachable from the menu bar.
  - Uninstall always confirms: set `uninstallCandidate`, and `RootView` shows the dialog, with a second "and Delete App Data" button (`zap`) for casks that have a zap stanza (`Package.hasZap`). When `store.dependents(of:)` is non-empty (installed packages whose dependencies include it) the dialog explains why it can't, with no Uninstall button: brew would refuse. brew's own refusal also names indirect dependents; Caskroom lists only direct ones, which the page shows as Used By.
  - Every package page ends with a Terminal section (`CommandList`): the brew command behind each action `store.commands(for:)` offers, with Copy. `BrewOperation.command` is the one source of that text, in the activity log too.
  - Maintenance: Clean Up (`BrewOperation.cleanup`, previewed by a `brew cleanup --dry-run` banner on Updates) and Export Brewfile (`.dumpBrewfile`, File menu, after a save panel) are queued operations. Doctor isn't: it changes nothing, so `store.runDoctor()` runs it directly for `DoctorSheet` (Package ▸ Run Doctor…). `brew doctor` writes warnings to stderr and exits 1 when it has any; `BrewService.doctor()` treats that as a result.
  - Activity: `ActivityPill` (toolbar, principal) shows the running or last operation; its popover is `ActivityView`, with logs capped at `OperationRun.logLimit` lines. Download progress: brew prints none without a terminal, so `store.watchDownloads` reads its cache (`brew --cache`) every half second while an operation runs: brew downloads to `downloads/<SHA-256 of the URL>--<file>.incomplete` and renames it when done (`BrewDownloads`, `DownloadTracker`). A cask's size comes from a HEAD request to its `downloadURL`, so it gets a fraction; bottle URLs aren't known here, so formulae show bytes only. `store.download` drives a filling ring (`DownloadIndicator`) in the pill and `PrimaryActionButton` ("Downloading") and a bar with size and speed in the Activity row. A download that finishes within one look (most from GitHub or a CDN) shows nothing. The popover opens by itself only when an operation fails. `Notifier` posts a notification when one finishes while Caskroom is in the background (skipped without a bundle, e.g. `swift run`); permission is asked on the first enqueue you make, or before the first updates-available notification if nothing has asked yet, never at launch.
  - `AppDelegate` owns the `BrewStore` so `applicationShouldTerminate` can ask before quitting with operations pending, then `stopAll()` before replying.
  - macOS attributes brew's Apple Events (`osascript`) to Caskroom. Quitting a cask's app before an upgrade needs no permission; removing a login item (`uninstall login_item:`, through System Events) raises the Automation prompt, which shows `NSAppleEventsUsageDescription` from `Support/Info.plist`.
  - macOS 15 support (`Compat.swift`): Liquid Glass APIs are macOS 26+, so every use goes through a fallback that keeps macOS 26's look as it is and gives Sequoia what its own apps had: `glassButton(prominent:)` (bordered / bordered prominent), `AnyTransition.drawOn` (a fade), and `if #available(macOS 26, *)` around `ActivityPill`'s glass (filled capsules on 15) and the toolbar's `sharedBackgroundVisibility`. Any new glass API needs one too, or the build fails. Sequoia's toolbar also hangs the whole app in an endless layout loop (100% CPU, a spinner before the first load) when a popover bound to the store sits directly on a toolbar item's view, so `ActivityPill` anchors its popover to a `Color.clear` background instead. A Sequoia Mac is reachable over SSH for checks like this (ask for the details); it found that one in minutes, where code reading found nothing. macOS draws glass only for apps whose binary is stamped with the 26+ SDK, and SwiftPM stamps the deployment target (15.0) instead, so the Makefile's `LINK_SDK` relinks with the real SDK version: a plain `swift build` binary runs in the pre-glass look on macOS 26+.
- Liquid Glass is for controls only (buttons, the toolbar pill); content such as banners and the in-row progress capsule uses materials or fills.
  - Motion (`Motion.swift`): only on state changes brew or the user caused, never decorative or looping beyond progress. Animate in views with `.animation(_:value:)` keyed to what changed, never in `BrewStore`. List row animations go through `Motion.list(reduceMotion:)` (none under Reduce Motion) and slide-ins through `.move(from:reduceMotion:)` (a fade under it); symbol effects adapt on their own. Pages show a `ProgressView` until the first refresh (`lastRefreshed`), so lists appear whole instead of animating every row in at launch. `store.settling` holds the finished operation until the next refresh lands; `PrimaryActionButton` shows its checkmark or failure mark for at least a second over that gap, so it never flashes Install after an install. `DrawnSymbol` draws a success symbol in once, only for a result that just arrived (Updates reaching zero while you watched, a clean doctor), never on simply opening a page. `ActivityPill` draws its own glass in a `GlassEffectContainer` (its toolbar item hides the shared background) so the glass can morph: the pill fits its title, a "+N" droplet splits off while commands are queued (`glassEffectID`, `.matchedGeometry`), and the glass tints green or red for a moment when `store.settling` changes. Glass motion uses `Motion.liquid`.
  - Every `List` of package rows sets `defaultMinListRowHeight`. Rows inserted into a list that started empty (every list at launch, while brew loads) otherwise keep AppKit's 24pt default and render clipped. Its `0-launch.png` capture is the check: later captures recreate the list and hide the bug.
  - `SnapshotDriver` (debug builds only) draws its own window into PNGs, which needs no Screen Recording permission. With `CASKROOM_SNAPSHOT_SCREEN=1` it uses `screencapture -l` instead: the real window, glass, sidebar and shadow included, for the site's screenshots (`docs/assets`, via `make screenshots`, whose `SHOTS` maps scenes to file names). That needs the permission for whatever runs the binary (Claude has it on this Mac); launched with `open`, Caskroom itself would need it, so run the binary directly. It activates its window first (`activate(ignoringOtherApps:)`; plain `activate()` doesn't take focus from a directly launched binary), since an inactive window draws dimmed. `CASKROOM_SNAPSHOT_ONLY` lists the scenes to capture (the rest still apply, unwaited, since later scenes build on their state) and skips the popover and Doctor, about 15 s instead of 3 minutes. Unless `CASKROOM_SNAPSHOT_FAKE_UPDATES=0`, it first fills in, on the store only and never on disk, what a fresh machine lacks: updates, an open app's update, a cleanup banner, update history, a deprecated package, and a running and a failed service. Glass, vibrancy (the sidebar's rows) and glass button labels don't render in the self-drawn captures, so judge layout from them, not materials. A `.glassProminent` button (Install on an uninstalled package's page) blanks the whole header around it in a capture; it draws fine on screen.

## App icon

`Support/AppIcon.icon` is an Icon Composer bundle (open it in Xcode ▸ Open Developer Tool ▸ Icon Composer, or edit `icon.json` and the SVG layers in `Assets/`). `make app` compiles it with `actool` into `Assets.car` + `AppIcon.icns`; actool needs absolute paths, hence `$(CURDIR)`.

## Known limitations

- Changing an existing app bundle in place (adopting runs `chgrp -hR admin` over it) needs macOS App Management permission for the app brew runs under, Caskroom here; without it brew fails with `Operation not permitted` and `OperationRun.blockedByAppManagement` explains and links the settings pane. Caskroom is ad-hoc signed, so macOS may forget that permission after each `make app`.

- Commands run as root by sudo ignore our SIGTERM; sudo forwards it, but an installer may still finish.
